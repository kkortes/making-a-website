# Making a website

The site is a journey told in steps, possibly hundreds of them, from a bare index.html to a fully fledged website. We work through them one at a time: the developer describes what the next step should contain, and the agent builds it with the smallest possible additions. Nothing more than the step asks for.

## Minimal changes

- The diff panel always shows the exact code change between two steps; never filter, fold or hide anything to make it look smaller.
- Each step makes one simple change. Keep the DOM minimal (no wrappers or elements the lesson doesn't need, no unused styles) and keep the markup steps share identical, same lines and same indentation, so the diff between consecutive steps shows only what that step teaches.
- Format markup one element per line: every nested element opens on its own line, indented two spaces inside its parent. Inline text-level elements (`<a>`, `<strong>`, `<q>`) start their own line too, with the text around them on the lines beside them.
- Wrap code written in a step's text in `<code>`: element names and tags, attributes, file names and API names (`the <code>&lt;main&gt;</code> lives in <code>components/Layout.html</code>`), link text included. It stays inline in the sentence, with the wording unchanged.

## Adding a step

- Steps 1–3 are plain HTML: no Vibe, no bindings, no `$.` handlers, no `<component>`; only the journey's chrome (bar, panes, sweep, gating) uses Vibe. Step 4 (Vibe) brings it into the steps: from then on the step's `index.html` loads Vibe in a `<script type="module">` in `<head>` (`import vibe from '/node_modules/@ape-egg/vibe/index.js'` and `vibe()`) and its body holds only `<component src="/components/Layout.html">` with `<component src="/components/PageContent.html"></component>` nested inside it; the step's own `components/Layout.html` (never the journey's) is `<main class="step">` around a `<slot></slot>` that takes what's nested in it, and its `components/PageContent.html` holds all of the step's content, with no `<main>` of its own: components can hold other components. Its `package.json` shows Vibe installed, one line in `dependencies` (`"@ape-egg/vibe": "^4.3.14"`, the package `index.html` imports), and every later step keeps that line. Step 5 (Compiled) swaps those for `<Layout>` and `<PageContent>`, Vibe's tags for components named after their files, and adds its `vibe-compiler` settings to the step's `package.json` (`"componentsAsIs": false`, so the compiler puts components into the page rather than leaving them for the browser to fetch; tags named after a component are inlined either way); only Vibe's compiler resolves such a tag. The journey mounts both forms itself (see the step's CSS below). Still no bindings or `$.` handlers until a step asks for them.
- Copy the previous step's folder to `steps/<n>/` and change only what the step asks for. The folder is the step's whole file system, its root the step's `/`, plus any stylesheet its `index.html` links from the site's root that the folder doesn't have (`/stylecheat.css`): the panel lists those files and diffs them against the previous step's. Step 1 lives at the address `/`, step n at `/<n>`; each step's files are served at `/<n>/…`.
- Each `index.html` is a normal document whose `<title>` is always `Making a website`. Add the step's name to `titles` in `steps.js` for the bar.
- The body holds one `<main class="step">` (from step 6 on just `<main>`, see the step's CSS below) (from step 4 on its `components/Layout.html`, through `<component src>` and from step 5 on `<Layout>`, wraps the nested `components/PageContent.html`, which holds the content, in `<main class="step">`), the element the step's CSS targets; inside it, in order: the `<h1>`; from step 2 on, right under it with no heading, a paragraph or two on what this step's change solved; then the checkbox label, where the step has one; then `<h2>Dive deeper</h2>` and the references list, where the step has them; then `<hr />`, the step's one rule, and `<h2>What's next</h2>` with a paragraph or two on the problem the following step deals with (on the last step, a general look ahead, never an invented step); then the next step's name and Next (from step 6 on inside the sticky bar below). No other wrappers.
- Right below the What's next paragraphs comes the next step's name, then Next, which calls `nextStep()`:
  ```html
  Step <n+1>: <title>
  <button id="next" onclick="nextStep()">Next</button>
  ```
  From step 6 on Next is Stylecheat's `primary` button and the two sit opposite each other in a Stylecheat `<crow justify-between>` inside a `<sticky>` pinned to the bottom, the last thing in `<main>`. `reverse` moves the sticky from `top` to `bottom`, `bg-background` gives it the sidebar's colour (Stylecheat's `--sidebar` is `--background`, and it has no `bg-sidebar`) and keeps the text scrolling under it out of sight, and `mt-auto` pushes it to the bottom of a short page. `<main>` is a column for that (`vertical left`), so the sticky needs `w-full` to span it:
  ```html
  <sticky reverse bg-background mt-auto w-full>
    <crow justify-between>
      Step <n+1>: <title>
      <button id="next" onclick="nextStep()" primary>Next</button>
    </crow>
  </sticky>
  ```
  `nextStep()` is the journey's own JavaScript (in `index.html`), never in a step file, so it never shows in the diff: it moves to the next step through Vibe's router, with no page load, and the sweep runs. A step opened on its own has no `nextStep()`, so its Next does nothing there. To make the reader tick a box first, start Next `disabled` and put this right after the paragraph that asks for the tick, just above the Dive deeper list (or the `<hr />` where there's none) in every step; its own JavaScript enables Next (and the journey listens to the same change for the panes):
  ```html
  <label>
    <input type="checkbox" onchange="document.getElementById('next').disabled = !this.checked">
    Label
  </label>
  ```
  The last step (now step 9) ends the journey: its bar holds `The end of the journey` and no Next, promising no next step. Adding a step after it gives it the next step's name and Next back.
- Just above the `<hr />`, after the checkbox label where there is one, add `<h2>Dive deeper</h2>` and a plain `<ul>` of references (MDN, web.dev or well-known articles) on the issue this step just solved, one per issue, each `<a>` with `target="_blank"`. The agent finds them while building the step and checks each link works. Step 1 solves nothing yet, so it has none, and a later step can have none too; without references there's no heading either.
- Use the developer's wording as given; fix only obvious spelling slips.
- Keep step text brief: the step's key point (what changed and why it matters), with no repetition and nothing the diff, the Next label or the next step already says.
- A step's own CSS is classic: every rule targets `.step` (`.step { … }`, `.step button { … }`; the reading column is `.step`'s own `padding-inline: max(2rem, 50% - 20rem)`, so the bare Next line sits in it too), the same selector in every step so the selector lines never show up in a step's diff. Only a rule that's about the page itself stays on `html`. A step's CSS only ever reaches its own step, even mid-sweep with two steps on the page: the journey mounts each step from `steps.json` (`mounted` in `index.html`), inlining the stylesheets it links from its own folder and wrapping every rule but the `html` ones in `@scope`, so they stay inside the step's `<component>`, and mounting each of its components, as `<component src="/components/Layout.html">` or a tag named after it (`<Layout>`), inline with that file (or its code-mode draft) and the tag's children in its `<slot>`, as Vibe's compiler inlines it, again until none is left, since one component can hold another; `html` rules are the page's, shared while the step is on it. A component drops `<body>`, so the step's body mounts as a `<step-body>` that keeps the body's attributes. A step never sets its own height: the journey stretches every step to the space under the bar (`step-body main` in `layout.css`, by element, so it reaches a `<main>` with or without the class). `<stage>` itself has no height and follows its step. The journey's bar scrolls away with the page, so Stylecheat's `sidebar { height: 100dvh }` would make a step one bar taller than the window. `step-body sidebar` in `layout.css` sets `height: auto` and `max-height: 100dvh` instead, so the sidebar stretches with its row. A short page fits the window exactly. On a long page the sidebar stays one window tall and sticks at the top, with no gap under it once the bar has scrolled away. Step 1 has no CSS, step 2 keeps it in a `<style>` in `<head>`, and from step 3 on it lives in the step's own `style.css`, linked from `<head>` with `<link rel="stylesheet" href="/style.css">`, the step's root, the same line in every step that has it. The journey inlines it from the step's files; a step opened on its own at `/<n>/index.html` asks the site's root for it, which has none, so only the journey styles it. From step 6 on the step is styled by Stylecheat instead: `<link rel="stylesheet" href="/stylecheat.css">` in `<head>` (the site's own copy, which every step from 6 on links as it is), `<body stylecheat>`, `<main pt-8 vertical left up f-1 bg-card>` in `components/Layout.html`, as step 7 has it (`up` and `f-1` only take effect where `<main>` sits in a flex row with a height, as it does from step 7 on) (without `class="step"`, since it has no CSS of its own; `bg-card` gives the content area Stylecheat's `--card`, the colour of the Stylecheat website's content card), the `<slot>` directly inside `<main>` in `components/Layout.html`, and the content of `components/PageContent.html` wrapped in `<container typography>` (Stylecheat's full-width `display: flex` column, up to 1280px; its typography spacing reaches only its direct children, so it sits on the content's own root rather than around the slot), with the sticky bar right after `</container>`, outside it, so it's a flex child of `<main>`: its `mt-auto` pushes it to the bottom of a short page, and it sticks to the bottom of the screen while a long one scrolls, every `<a>` in the step's content `primary`, and no `style.css`; the journey's `display: flow-root` on the step's `<main>` only applies to steps without Stylecheat, so `vertical` takes effect.
- From step 7 (Multi-page Application) on a step can have more pages than its `index.html`, which stays in the step's root: each further page is a full document in `pages/` (`pages/about-me.html`) with the same `<head>` and `<body stylecheat>` as `index.html`, its body `<Layout>` with the page's own content inside it. `components/Layout.html` then holds `<MainNav>` beside `<main pt-8 vertical left up f-1 bg-card>` (around its `<slot>`) in a `<crow stretch>` (the sidebar needs a flex row to sit in; `f-1` gives `<main>` the rest of it, and `up` keeps a page without the sticky bar at the top). `components/MainNav.html` is a Stylecheat `<sidebar>` that links every page from the step's root (`/index.html`, `/pages/about-me.html`) as `tertiary` `.button`s in a bare `<sidebar-content>` (Stylecheat's own `--sidebar`, the page background, as on the Stylecheat website), their `<crow>` followed by `<Rail></Rail>`. `components/Rail.html` is a square `<svg w-full>` rail: a light gray `<rect>` (`style="stroke: var(--border)"`, since Stylecheat has no `text-border` and an SVG `stroke` attribute takes no `var()`) under a `text-primary` one whose `<animate>` runs its `stroke-dashoffset` from `100` to `-100` over `8s` (`pathLength="100"`, `stroke-dasharray="100"`, `stroke-linecap="square"` so each end of the fill covers a whole corner and it starts and ends at a clean right angle), so primary fills the rail clockwise and gray fills it back, in a loop, with no other CSS. `<sidebar-content>`'s `justify-content: space-between` puts the rail at the bottom, inset by its padding; the nav's `<crow>` has no `up`, whose `height: 100%` would squeeze it. `components/BottomBar.html` is the sticky bar, the `<sticky>` with the next step's name and Next inside it. There's no `components/PageContent.html`: each page holds its own content inside `<Layout>`, its `<container typography>` followed by `<BottomBar></BottomBar>` (`index.html` and `pages/about-me.html` alike), so the bar lands in `<main>` after the content (the page places it rather than `Layout.html`). Every page has its own address: `index.html` the step's, `pages/<page>.html` `/<n>/<page>.html` (`pages` in `steps.js`, so `/7/about-me.html`; `vercel.json` serves the journey there too). The journey routes each one, mounts it as it mounts `index.html` and points the step's links to its pages (`/pages/about-me.html`) at their addresses; moving between pages of the same step swaps the page in with no sweep (`onNavigate` in `index.html`), the page's file is the one the file viewer opens, the step stays marked in the bar, and leaving the page drops all edits.
- Step 8 (Single-page Application) has Vibe's compiler build the step as an SPA, changing only what that takes: `"spa": true` in its `package.json`'s `vibe-compiler` (above `componentsAsIs`, so the diff adds one line), its home page moved from `index.html` into `pages/index.html` (in SPA mode the compiler writes the one shell `index.html` itself out of the pages tree, overwriting a root one), and every link to a page pointing at the route Vibe names after its file, the router claiming only links that match a route (`/` and `/about-me` in `MainNav.html`, and about-me's Back home). Its `components/Rail.html` is step 7's as it is, rendered from its own `MainNav.html` the same way. A step with `"spa": true` (`spa` in `steps.js`) has its home at `pages/index.html` (`home`), which the journey mounts, links stylesheets from and diffs against the previous step's home, marking it `moved` (blue in the file viewer) rather than listing `index.html` removed and `pages/index.html` added; its pages' addresses drop `.html` (`/8/about-me`, which `vercel.json` serves the journey at too), and `links` in `steps.js` maps each link the step's pages use (`/pages/about-me.html`, or `/about-me` in an SPA) to its address for `mounted`. Vibe's compiler (4.3.15 or later) hoists a layout into the shell when every page's body is the same one layout, as `<component src>` or a tag named after it, so step 8's `<Layout>` mounts once and moving between its pages swaps only what's in its `<slot>` (its rail keeps running). The journey does the same for every such SPA step (`hoisted` in `index.html`): all its pages route to one shell, `mounted`'s `'shell'`, its home page with `<component src="@[outlets['/8']]">` in the layout's `<slot>`, and each page's `'fragment'`, the page with only what's in its layout, is what `onNavigate` puts in `$.outlets` for the step. A code-mode edit in such a step re-renders through the shell and the outlet, so an edit inside the layout remounts only the outlet, and leaving the page routes back to the clean shell. Blob addresses are one per distinct text (`blob`), so a shell that renders the same keeps its address and stays mounted.
- Step 9 (Reactivity) replaces everything repeated in the markup with Vibe reactivity and brings the journey's first `.js` file: `state.js` in the step's root, `export default` the initial state (the sidebar's `pages`, about-me's `projects`, the home page's `reading` (its Dive deeper links, each with `href`, `title` and `source`), `guest` and `guestbook`), which every page's `<head>` imports (`import state from '/state.js'`, then `vibe(state)`, the same lines on every page). Lists render from it with `<!-- each pages as link -->` (the `<sidebar>`'s links in `MainNav.html`, about-me's cards, the home page's Dive deeper links), values show through `@[…]`, the sidebar marks the page you're on with Stylecheat's `active` (`active="@[page.path === link.href]"`, against the path in Vibe's router's `$.page`, so it follows navigation; Vibe sets a bound `active` when true and removes it when false), with a `--card` background (`sidebar a[active]` in a `<style>` at the top of `MainNav.html`, scoped to the step by the journey like any step stylesheet), since Stylecheat's own active tint in a sidebar is `--background`, the sidebar's own colour, and the home page's guestbook plays with it: an input (`oninput="$.guest.name = this.value"`), a slider and a button that pushes the guest onto `guestbook`. Its `components/Rail.html` is step 8's as it is, and `MainNav.html` renders `<Rail></Rail>` after the links in a `<crow>` without `up`, as step 8 does, so the rail shows no change between the two steps. A `@[…]` meant as text in the step's prose is `<code vibe-dehydrate>`, so Vibe leaves it as written. The journey runs the step inside its own Vibe: the step's `vibe(state)` only adds keys `$` doesn't have yet, so the step's state lives on the journey's `$` for the rest of the visit (and keeps its values when the step is left and reopened), and its keys never reuse the journey's (`page`, `steps`, `panes`, `open`, `mode`, `drafts`, `sweep`, `outlets`, …). `mounted` points a module script's import of one of the step's own files (`/state.js`) at that file (or its code-mode draft) as a blob, with the step's page links in it (`'/'`, `'/about-me'`) pointed at their addresses as it does for `<a href>`, since a link rendered from state has no `href` to rewrite until Vibe renders it.

## Dev server

- The developer keeps `bun run dev` running at https://making-a-website.localhost while agents work, and it hot-refreshes every edit. Never stop, kill or restart it, never start a second one, and don't run `bun run build` to see a change: check your work against the running server.

## Setup

- `index.html` is the journey itself: one Vibe page that sets up Vibe's router by hand from `steps.json` and renders each step's `index.html` into the content area. It's served at every step's address, so it names its one hydration manifest the way Vibe's SPA shell does. Only the build has that manifest; in dev its request 404s and Vibe renders without it.
- `steps.js` reads `steps/` into the steps list (route, src, title, files with before/after/state; `index.html` leads the files, the rest following by path, root files before nested ones and stylesheets after everything else, so they sit at the bottom of the diff pane and of each folder in the file viewer); a stylesheet a step links from the root that its folder doesn't have (`<link rel="stylesheet" href="/stylecheat.css">`) is the site's: it joins its files under its root path and its path joins the step's `site`, the links the journey leaves as they are, so step 6 shows `stylecheat.css` added in full and later steps list it unchanged. In dev, `vite.config.js` serves it live at `/steps.json` and makes `steps/` Vite's public folder, so each step's files are served raw at `/<n>/…`; `vite.config.js` imports `steps.js`, so Vite restarts the server itself when `steps.js` changes, and the address drops until it's back. `bun run build` writes it to `compiled/steps.json` and copies `steps/` as it is (the compiler skips it).
- `components/Layout.html` + `layout.css`: the step bar, the panes, the content column (`<stage>`, so a step's own `<main>` is the only one), the divider sweep (one `sweep.position` value, 0–1, through `--divider`), the checkbox listener and the page's scrollbar (always shown, `overflow-y: scroll` on `html`, coloured like the dark Codie panes: `oklch(0.4 0.02 264)` on `#15181d`, copied from Codie's dark theme in `theme.css` (`--codie-scrollbar-thumb` on `--codie-bg`), since Codie only sets those on its own elements; keep them in step when Codie's dark theme changes). `scrollbar-color` inherits, and in Chrome any value but `auto` turns off `::-webkit-scrollbar` styling, so `body` sets it back to `auto`: the colour stays on the page's own scrollbar, and the panes keep Stylecheat's scrollbars and the codies their own.
- Step 1 shows only the bar and the content until its box is ticked, which slides in the diff pane right of the content; it stays from step 2 on. Ticking Adding styles' box slides in the file viewer left of the content; it stays from step 3 on, the first step with two files (`panes` in `index.html`). With the file viewer comes a circle in the content's top right corner that toggles code mode: an editable Codie (`@ape-egg/codie`) holding the step's `index.html` in place of the content; edits re-render the content and update the diff. A step whose `package.json` has `dependencies` (`installed` in `steps.js`) also shows `node_modules/` at the bottom of the file viewer, with a grey `...files...` line beneath it: a placeholder only, with no files behind it and nothing in the diff. The file viewer marks the open file, `index.html` when the step loads; clicking another file (like `style.css`) opens it in code mode only, with no circle; an HTML file's edits re-render the content, a CSS file's restyle the page (through its inlined, scoped `<style>`), and each updates its diff; a JS file's (`state.js`) update only its diff, since its state applies when the step mounts and `$` already holds it. Clicking `index.html` returns to the page; leaving the step drops all edits.
- Each changed file in the diff pane is a `<code-diff>` in `Layout.html`: a `<codie data-path>` drawn by Codie's diff mode (`codie({ el, diff: true, numberedRows: true, before })`, made and redrawn by `redraw` in `index.html` whenever the step's file or its code-mode draft changes), then a Stylecheat `<sticky auto-shadow>` header with the path in `<code>` and a `+added −removed` tally that `code-diff.css` counts from Codie's rows with CSS counters. Each header sticks while its own block is in view and casts a shadow only while stuck. Codie owns the diff itself: added block above removed block, word marks only on lines that are the same line edited, every line shown, all rows drawn at once. A file whose diff has more than 500 lines added and removed combined (step 6's `stylecheat.css`) gets no `<codie>` at first: in its place sits a full-width `tertiary` Show changes button, and only pressing it (adding the path to `shown`, which empties when the step changes) puts the `<codie>` there for `redraw` to draw, so moving to the step never builds the big diff. The counts come from `lines` on each file in `steps.json`, which `steps.js` counts from the rows Codie's `diff` (`@ape-egg/codie/diff`) draws. The button seeds the tally's counters with them (`counter-set`), so the header shows them before any row is drawn.
- Stylecheat (`stylecheat.css`, a copy of `stylecheat/static/download/hybrid/stylecheat.css`, 2.0.0) styles the journey's chrome: it applies under `[stylecheat]`, which `<file-tree>`, the code-mode button and `<diff-list>` carry. From 2.0.0 its reset and typography are scoped under `[stylecheat]` too, so steps 1–5 keep the browser's defaults. Step 6 brings Stylecheat into the steps: from then on every step links this same file and its body carries `stylecheat` (see Adding a step). The step's folder has no `stylecheat.css`, so the link is the site's (in the step's `site`) and the journey leaves it as it is rather than inlining and scoping it; that's safe because every Stylecheat rule only reaches elements under `[stylecheat]`, which steps 1–5 never have.
- `@ape-egg/codie`, `@ape-egg/vibe` and `@ape-egg/vite-plugin-vibe` are linked to the local copies in `vibe/nodemodules/@ape-egg/` (`bun link @ape-egg/codie`, `bun link @ape-egg/vibe`, `bun link @ape-egg/vite-plugin-vibe`); the plugin needs 0.5.1 or later for step edits to hot-refresh. The compiler copies `node_modules` as they are (`nodeModulesAsIs`), so `compiled/` gets the linked packages rather than a registry install. Vite keeps the links at their `node_modules` paths (`resolve.preserveSymlinks`): resolved into the vibe checkout, the page's `/node_modules/@ape-egg/vibe/index.js` gets Vite's `?v=` dependency query while the runtime's own `./index.js` doesn't, the two load as separate instances and `ready` never fires. Vite serves them as cached dependencies, so after either changes upstream the developer restarts with `bun run dev --force`. The diff pane needs Vibe 4.3.14 or later: earlier versions keep an `each` row whose key changed when its markup didn't, so a step reached through Next showed a stale diff.
- `bun run dev` runs Vite (`vite.config.js`) with `@ape-egg/vite-plugin-vibe` behind `../dev.sh`, at https://making-a-website.localhost. It serves the raw Vibe page with no compile step and hot-refreshes edits: `components/` and `index.html` patch in place (a changed page `<script>` reloads), CSS through Vite. A step's `index.html` refreshes the mounted step in place and its `style.css` swaps in place (plugin 0.5.1 handles files Vite serves from its public folder). The diff pane keeps the `steps.json` the page loaded until the next page load. It runs under Bun (`--bun`) because `steps.js` uses Bun's file API.
- `bun run build` is the production build: Vibe's compiler (with the hyperspeed manifest) into `compiled/`, plus `steps.json` and the steps. Dev never reads `compiled/`.
