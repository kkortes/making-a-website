# Making a website

The site is a journey told in steps, possibly hundreds of them, from a bare index.html to a fully fledged website. We work through them one at a time: the developer describes what the next step should contain, and the agent builds it with the smallest possible additions. Nothing more than the step asks for.

## Minimal changes

- The diff panel always shows the exact code change between two steps; never filter, fold or hide anything to make it look smaller.
- Each step makes one simple change. Keep the DOM minimal (no wrappers or elements the lesson doesn't need, no unused styles) and keep the markup steps share identical, same lines and same indentation, so the diff between consecutive steps shows only what that step teaches.
- Format markup one element per line: every nested element opens on its own line, indented two spaces inside its parent. Inline text-level elements (`<a>`, `<strong>`, `<q>`) start their own line too, with the text around them on the lines beside them.

## Adding a step

- The steps are plain HTML: no Vibe, no bindings, no `$.` handlers, no `<component>`. Vibe gets its own step later in the journey; until then only the journey's chrome (bar, panes, sweep, gating) uses it, never a step file.
- Copy the previous step's folder to `steps/<n>/` and change only what the step asks for. The folder is the step's whole file system: the panel lists its files and diffs them against the previous step's folder. Step 1 lives at the address `/`, step n at `/<n>`; each step's files are served at `/<n>/…`.
- Each `index.html` is a normal document whose `<title>` is always `index.html`. Add the step's name to `titles` in `steps.js` for the bar.
- The body holds one `<main class="step">`, the element the step's CSS targets; inside it, in order: the `<h1>`; from step 2 on, right under it with no heading, a paragraph or two on what this step's change solved; then the checkbox label, where the step has one; then `<h2>Dive deeper</h2>` and the references list, where the step has them; then `<hr />`, the step's one rule, and `<h2>What's next</h2>` with a paragraph or two on the problem the following step deals with (on the last step, a general look ahead, never an invented step); then the next step's name and Next. No other wrappers.
- Right below the What's next paragraphs comes the next step's name, then Next, which calls `nextStep()`:
  ```html
  Step <n+1>: <title>
  <button id="next" onclick="nextStep()">Next</button>
  ```
  `nextStep()` is the journey's own JavaScript (in `index.html`), never in a step file, so it never shows in the diff: it moves to the next step through Vibe's router, with no page load, and the sweep runs. A step opened on its own has no `nextStep()`, so its Next does nothing there. To make the reader tick a box first, start Next `disabled` and put this right after the paragraph that asks for the tick, just above the Dive deeper list (or the `<hr />` where there's none) in every step; its own JavaScript enables Next (and the journey listens to the same change for the panes):
  ```html
  <label>
    <input type="checkbox" onchange="document.getElementById('next').disabled = !this.checked">
    Label
  </label>
  ```
  The last step has `Step <n+1>: coming soon` and `<button disabled>Next</button>` until the next step exists, so its button styles stay in use.
- Just above the `<hr />`, after the checkbox label where there is one, add `<h2>Dive deeper</h2>` and a plain `<ul>` of references (MDN, web.dev or well-known articles) on the issue this step just solved, one per issue, each `<a>` with `target="_blank"`. The agent finds them while building the step and checks each link works. Step 1 solves nothing yet, so it has none, and a later step can have none too; without references there's no heading either.
- Use the developer's wording as given; fix only obvious spelling slips.
- Keep step text brief: the step's key point (what changed and why it matters), with no repetition and nothing the diff, the Next label or the next step already says.
- A step's own CSS is classic: every rule targets `.step` (`.step { … }`, `.step button { … }`; the reading column is `.step`'s own `padding-inline: max(2rem, 50% - 20rem)`, so the bare Next line sits in it too), the same selector in every step so the selector lines never show up in a step's diff. Only a rule that's about the page itself stays on `html` (`html { scrollbar-gutter: stable }`, which only the root can carry: it reserves the viewport's gutter, and on `body` it does nothing). A step's CSS only ever reaches its own step, even mid-sweep with two steps on the page: the journey mounts each step from `steps.json` (`mounted` in `index.html`), inlining its stylesheets and wrapping every rule but the `html` ones in `@scope`, so they stay inside the step's `<component>`; `html` rules are the page's, shared while the step is on it. A step never sets its own height: the journey stretches every step to the space under the bar (`stage .step` in `layout.css`). Step 1 has no CSS, steps 2–3 keep it in a `<style>` in `<head>`, and from step 4 on it lives in the step's own `style.css`, linked from `<head>` with `<link rel="stylesheet" href="/<n>/style.css">`. From step 5 on the step also carries its own copy of Stylecheat, `<link rel="stylesheet" href="/<n>/stylecheat.css">` right above that, and its `<main>` carries `stylecheat typography`; the copy is Stylecheat's own file, so its rules don't follow the `.step` rule, and `style.css` keeps only what Stylecheat doesn't cover.

## Setup

- `index.html` is the journey itself: one Vibe page that sets up Vibe's router by hand from `steps.json` and renders each step's `index.html` into the content area. It's served at every step's address, so it names its one hydration manifest the way Vibe's SPA shell does. Only the build has that manifest; in dev its request 404s and Vibe renders without it.
- `steps.js` reads `steps/` into the steps list (route, src, title, files with before/after/state). In dev, `vite.config.js` serves it live at `/steps.json` and makes `steps/` Vite's public folder, so each step's files are served raw at `/<n>/…`; editing `steps.js` restarts the server. `bun run build` writes it to `compiled/steps.json` and copies `steps/` as it is (the compiler skips it).
- `components/Layout.html` + `layout.css`: the step bar, the panes, the content column (`<stage>`, so a step's own `<main>` is the only one), the divider sweep (one `sweep.position` value, 0–1, through `--divider`) and the checkbox listener.
- Step 1 shows only the bar and the content until its box is ticked, which slides in the diff pane right of the content; it stays from step 2 on. Ticking Steady scrollbar's box slides in the file viewer left of the content; it stays from step 4 on, the first step with two files (`panes` in `index.html`). With the file viewer comes a circle in the content's top right corner that toggles code mode: an editable Codie (`@ape-egg/codie`) holding the step's `index.html` in place of the content; edits re-render the content and update the diff. The file viewer marks the open file; clicking another file (like `style.css`) opens it in code mode only, with no circle, and its edits restyle the page (through its inlined, scoped `<style>`) and update its diff. Clicking `index.html` returns to the page; leaving the step drops all edits.
- Each changed file in the diff pane is a `<code-diff>` in `Layout.html`: a `<codie data-path>` drawn by Codie's diff mode (`codie({ el, diff: true, numberedRows: true, before })`, made and redrawn by `redraw` in `index.html` whenever the step's file or its code-mode draft changes), then a Stylecheat `<sticky auto-shadow>` header with the path in `<code>` and a `+added −removed` tally that `code-diff.css` counts from Codie's rows with CSS counters. Each header sticks while its own block is in view and casts a shadow only while stuck. Codie owns the diff itself: added block above removed block, word marks only on lines that are the same line edited, every line shown, all rows drawn at once.
- Stylecheat (`stylecheat.css`, a copy of `stylecheat/static/download/hybrid/stylecheat.css`, 2.0.0) styles the journey's chrome: it applies under `[stylecheat]`, which `<file-tree>`, the code-mode button and `<diff-list>` carry. From 2.0.0 its reset and typography are scoped under `[stylecheat]` too, so steps 1–4 keep the browser's defaults. Step 5 brings Stylecheat into the steps, and from then on every step carries its own copy of this file (see Adding a step); the chrome's copy isn't scoped to a step, so in the journey it styles a step's `<main stylecheat>` as well, and the step's copy is what styles it when it's opened on its own.
- `@ape-egg/codie`, `@ape-egg/vibe` and `@ape-egg/vite-plugin-vibe` are linked to the local copies in `vibe/nodemodules/@ape-egg/` (`bun link @ape-egg/codie`, `bun link @ape-egg/vibe`, `bun link @ape-egg/vite-plugin-vibe`); the plugin needs 0.5.1 or later for step edits to hot-refresh. The compiler copies `node_modules` as they are (`nodeModulesAsIs`), so `compiled/` gets the linked packages rather than a registry install. Vite keeps the links at their `node_modules` paths (`resolve.preserveSymlinks`): resolved into the vibe checkout, the page's `/node_modules/@ape-egg/vibe/index.js` gets Vite's `?v=` dependency query while the runtime's own `./index.js` doesn't, the two load as separate instances and `ready` never fires. Vite serves them as cached dependencies, so after either changes upstream restart with `bun run dev --force` (and rebuild). The diff pane needs Vibe 4.3.14 or later: earlier versions keep an `each` row whose key changed when its markup didn't, so a step reached through Next showed a stale diff.
- `bun run dev` runs Vite (`vite.config.js`) with `@ape-egg/vite-plugin-vibe` behind `../dev.sh`, at https://making-a-website.localhost. It serves the raw Vibe page with no compile step and hot-refreshes edits: `components/` and `index.html` patch in place (a changed page `<script>` reloads), CSS through Vite. A step's `index.html` refreshes the mounted step in place and its `style.css` swaps in place (plugin 0.5.1 handles files Vite serves from its public folder). The diff pane keeps the `steps.json` the page loaded until the next page load. It runs under Bun (`--bun`) because `steps.js` uses Bun's file API.
- `bun run build` is the production build: Vibe's compiler (with the hyperspeed manifest) into `compiled/`, plus `steps.json` and the steps. Dev never reads `compiled/`.
